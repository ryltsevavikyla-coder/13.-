# 13.Системы мониторинга

1. Минимальный набор метрик
Для платформы (HTTP-взаимодействие + CPU-нагруженные вычисления + сохранение текстовых отчётов на диск):

CPU: usage_user, usage_system, load1/load5/load15 — вычисления сильно грузят процессор, нужно видеть насыщение.
Память: used_percent, available — чтобы не упереться в OOM и понимать давление на RAM.
Диск: used_percent, free, inodes_free (или inodes_used_percent) — отчёты пишутся на диск, при большом количестве маленьких файлов inodes заканчиваются раньше места.
HTTP: rate запросов, latency (p95/p99), распределение кодов ответов (особенно 5xx).
Приложение (если есть): время выполнения job’ов / количество успешных отчётов.

Эти метрики покрывают Golden Signals (latency, traffic, errors, saturation) + специфику записи на диск.
2. Что предложить Product Manager’у
Вместо сырых RAM/inodes/CPU:

SLA/SLO-метрики: процент успешных запросов (2xx), p95/p99 latency, availability.
Бизнес-метрики: количество успешно сгенерированных отчётов, среднее время генерации отчёта, процент failed jobs.
Дашборды с понятными названиями: «Качество обслуживания», «Выполнение SLA», «Скорость обработки».
Алертинг по error budget (насколько быстро «сжигаем» бюджет ошибок).

3. Как дать разработчикам ошибки без полноценной системы логов

Настроить сбор логов ошибок через Telegraf (file input + grok/json parser) и превратить их в метрики (app_errors_total{type=..., service=...}).
Или: приложение пишет ошибки в stdout → Docker/journald logs → Telegraf docker/file input → метрики.
Плюс простой алертинг в Slack/Telegram. Для деталей можно временно включать debug-логирование по запросу. Полноценный ELK/Loki не нужен.
